Claude Code plugin - user guide

alfred-tools

One plugin that sets up 14 tested MCP servers for Claude Code and Cursor. You pick the tools and answer a few questions. It shows you a plan of every change and applies nothing until you confirm.

Commands
4, all typed by you
Tools
14 MCP servers
Apps
Claude Code and Cursor
Needs
Node 22.18+, the claude CLI

New to MCP?

An MCP server is a small program or hosted service that gives an AI assistant extra tools: reading GitHub issues, driving a browser, looking up current library docs. Claude Code and Cursor each keep their own list of the servers they connect to. alfred-tools writes those lists for you, keeps them in step, and repairs them when a machine or a project changes.

Get started

Add the marketplace and install the plugin once per machine:

claude plugin marketplace add envoydev/plugins-marketplaces
claude plugin install alfred-tools@envoydev

The plugin installs nothing on its own. Open Claude Code in the project you want the tools in, then:

  1. Run /alfred-tools:install. It prints the catalog for your operating system and marks what is already installed.
  2. Pick the tools you want.
  3. Say which apps the servers are for. 'Claude Code and Cursor' is recommended when Cursor is on this machine.
  4. Answer 'Use the recommended settings', or set each tool up one at a time. Which settings to pick explains every question.
  5. Read the plan: every claude call and every file it writes. Answer 'Apply'.
  6. For a tool that uses a key, open the .mcps-secrets file the plan names and write the value after NAME=. The plugin never asks for a key, reads one out or prints one.
  7. Restart Claude Code, or use /mcp, pick the server and choose Reconnect. Restart Cursor too if it got the servers. The plan's last lines say what each server needs.

The four commands

Each command does one job. They are manual: a command runs only when you type it, and Claude never starts one by itself. Run them from your project folder.

CommandUse it whenWhat it touches
/alfred-tools:installYou want a tool this project does not have yet.Adds only. It never changes, moves or removes what is there.
/alfred-tools:configureYou want to change or remove something installed.One server or root folder at a time, starting from what it has now.
/alfred-tools:fixA server will not start, or you moved or cloned the project.Only the known problems it finds and you pick.
/alfred-tools:updateYou updated the plugin, or want newer server versions.Versions that are behind, to releases at least 7 days old.

The shape of every run

All four follow the same order, so you always know where you are. The two steps in amber are yours.

  1. ReadLooks at what is installed. Starts no server.
  2. AnswerEach question has one recommended option, listed first.
  3. PlanLists every call and every file it will write.
  4. ConfirmNothing has changed before this point.
  5. ApplyMakes each change, reads it back, stops at the first failure.
  6. DownloadFetches new packages in the background and starts each server once.
  7. RestartNew servers load when Claude Code starts again.
  • Two guards on every change. Besides the plan's own question, Claude Code shows its permission prompt for the step that writes. The plugin pre-approves only the steps that read.
  • Go straight to one tool by naming it: /alfred-tools:configure sentry.
  • Your own servers are safe. A server you added yourself is listed, never offered and never touched.
  • If a change fails, what was already applied stays and is named. A failed rewrite prints a RESTORE BY HAND line that puts the registration back. A key in that line shows as ${ALFRED_TOOLS_KEPT}, never its value.

/alfred-tools:install

[tool id]

Adds tools that are not installed in this project.

What happens

  1. The catalog. Prints every tool for your operating system, numbered, with what is installed at each scope.
  2. Pick. You choose from the tools not installed here, grouped as Code, Docs and forges, Browsers, and Machine.
  3. Apps. 'Claude Code and Cursor' or 'Claude Code only'. Asked once for the whole run.
  4. Settings. 'Use the recommended settings' ends the questions here. Otherwise each tool is asked in turn: its route, scope and name, the root folder, its data folder, then its key name and settings.
  5. Prerequisites. Checks only what your picks need: uvx, npx, Docker, a browser, the Android SDK, a JDK. For a missing one you choose 'Skip this tool' (recommended), 'Install it now' or 'Register anyway'.
  6. Plan and confirm. 'Apply', 'Change something' or 'Cancel'.
  7. Apply and download. Registers each server, then downloads its package in the background and starts it once, so your next session connects quickly. Restart only after the download reports.

Good to know

  • A tool already installed for every project (Global) can get this project's own copy beside it. The global one is not changed.
  • A tool that already reaches you through a claude.ai connector or another plugin is labelled in the list. Picking it adds this project's own registration beside the other.
  • To change or remove something installed, use configure. Install will point you there.

/alfred-tools:configure

[registration name | tool id]

Changes or removes what is installed, one server at a time.

What happens

  1. Menu. 'Change tools', 'Remove tools' or 'Done'.
  2. Pick. One option per installed server (a tool at two scopes is two options), plus servers left on their own and the root folders in use.
  3. Who looks after it. The first question about a server. 'alfred-tools' goes on to the settings. 'Leave it on its own' ends there, and configure, update and fix skip that server from then on. Configure hands it back whenever you want.
  4. Settings. Route, scope, name, data folder, key or OAuth, key name, extra settings, and which apps it is set up for. Every question recommends what the server has now, so keeping the answers changes nothing.
  5. Plan, confirm, apply. A plan that says 'Nothing to do' means every answer kept what is installed.

Good to know

  • It starts from what is installed, not from the catalog. A version you updated, and any arguments or environment values you added, stay.
  • A scope change is a move. A Global server moved to Local is gone from your other projects. To keep it there and add a copy here, use install.
  • A rename or move is done safely. The new registration is added and read back before the old one is removed.
  • Moving a data folder or a root folder moves no data. The plan names the old folder. You copy what you want to keep, including values in .mcps-secrets.
  • Removing a server takes it out of both apps. Its data folder and key file stay where they are.

/alfred-tools:fix

[tool, registration name or fix id]

Finds known problems in what is installed and applies the recorded fix for each.

What happens

  1. Detect. Lists each problem found: its fix id, the server and what is wrong. A line ending 'NOT APPLICABLE' gives a reason, and that reason is the advice. Nothing found prints 'No known problem found.'
  2. Choose. 'Apply all found' (recommended), 'Pick which' or 'Skip'.
  3. Hand edits. When one app's copy of a server was changed by hand, you are asked per server: 'Keep the change' (the list and the other app take it) or 'Restore from the list'.
  4. Apply and check. Each fix is checked by running its detector again, and reported as 'fixed' or 'STILL FOUND'.

Run it after

  • moving a project folder, or cloning a project onto another machine (the paths it wrote are absolute);
  • changing the key of a local server such as github in Docker (fix writes the new key into its registration);
  • a server that will not start or connects without its key. When something is wrong lists what it knows.

/alfred-tools:update

no argument

Brings what is behind up to date, and moves older setups to the way the plugin works now.

What happens

  1. Check. Refreshes your marketplaces and lists what is behind: installed plugins, pinned servers as current -> offered with the release's age, and the helper files in each root folder. It also lists releases held back, and what it could not check. 'everything current' ends the run.
  2. Choose. 'All of them' (recommended), 'Pick which' or 'Skip'.
  3. Cursor. If Cursor is on this machine and a root's servers are set up for Claude Code only, it offers once to add Cursor. 'Not now' is remembered.
  4. Apply and download. Each updated server is removed and added again under the same name, scope and settings. Only the version moves. The new packages download in the background.

Good to know

  • The 7-day rule. A version moves only to a release at least 7 days old. A newer, younger release is shown as held back and never offered.
  • What has no version to move: a hosted server (it is a URL), a Docker image tag, and a server left on its own.
  • After a plugin upgrade it also moves what an older version wrote: a key kept in a registration moves to .mcps-secrets once you have put it there, relative paths become absolute, and the root's .gitignore gains missing lines.
  • Cursor asks you to approve a server again whenever its entry changes. The report names each one.

The plugin itself is updated from your terminal. Updates are pulled, never pushed:

claude plugin marketplace update envoydev
claude plugin update alfred-tools@envoydev

Then run /alfred-tools:update in each project.

The tools

Fourteen MCP servers, each tested in Claude Code and in Cursor. A tool that works in one app only is not in the catalog. Every package is pinned to an exact version; the ones shown here are the catalog's in 0.6.0.

Code

serena

local

Code navigation that understands symbols, not just text.

serena starts a language server for your project and answers structural questions: what a file defines, where a symbol is declared, what implements an interface, and everything that references a symbol. That is more reliable than a text search when a name is common or reused.

The plugin runs it with its own context file, serena-context.yml, which gives it navigation tools only: get_symbols_overview, find_symbol, find_declaration, find_implementations and find_referencing_symbols. Reading, editing and searching files stay with the app's own tools. Its web dashboard and usage reporting are off.

memory

local

A memory that lasts across sessions.

Runs mcp-memory-service with a local SQLite database. Claude can store notes and decisions and search them later by meaning, so a new session can pick up what an earlier one learned. Nothing leaves your machine.

The database follows the scope you install at: Global is one memory shared by every project, Local or Project is this project's own. The first start downloads an embedding model, which takes about 2 minutes. Install does that in the background.

Keys

Every key lives in one plain text file per root folder, .mcps-secrets. The plugin writes the names. You write the values.

# keys for the hosted servers - never commit this file
GITHUB_PERSONAL_ACCESS_TOKEN=github_pat_...
ATLASSIAN_API_TOKEN=me@example.com:ATATT3x...
CONTEXT7_API_KEY=ctx7sk-...   # a note after whitespace and # is not part of the value
  • The plugin never handles a value. It does not ask for a key, read one out or print one. It names the file and the name, and tells you whether the value is filled.
  • One key can serve every project. The key is looked up in the .mcps-secrets beside the helper first, then in the global root's. The first value found wins.
  • Changing a key is: edit the file, then /mcp, pick the server, Reconnect.
  • Kept out of AI sessions. The plugin adds a deny rule to your Claude Code settings so a session's file tools and the shell's cat, head, tail and sed cannot open .mcps-secrets. A grep -r from a folder above, or a script, can still read it unless Claude Code's sandbox is on (/sandbox; not on native Windows), and a key written into a local server's entry (github in Docker, sentry with npx) sits in the account file and ~/.cursor/mcp.json, which no rule covers. The file is still plain text, so keep it out of anything you share. The root's .gitignore keeps it out of git.

How a server gets its key

A hosted server in Claude Code. A small helper script runs each time Claude Code connects and hands over the key. The registration itself holds no key.

.mcps-secrets→mcp-headers.js→the vendor's server

A hosted server in Cursor, or a bridge route. Cursor does not run Claude Code's helper, so its copy starts a small bridge that reads the same file and passes the key on in memory, never on a command line.

.mcps-secrets→mcp-bridge.js→mcp-remote→the vendor's server

A local server with a key (github in Docker, sentry with npx). The key is written into the registration when you apply, at Local or Global scope only, so it never lands in a file you commit. After you change the key, run /alfred-tools:fix to write it again.

.mcps-secrets→the registration→the local server

How it works

One list, two apps

Claude Code and Cursor read different files, so a server set up in one is invisible to the other. Each root folder keeps one list, mcps.json: every server the plugin manages there, which apps it is for, and the entry each app gets. It never holds a key. Every command writes both apps from that list in the same run.

The list<root>/mcps.json
What is managed, and for which apps
Claude CodeWritten through the claude CLI: .mcp.json and your account file
CursorWritten by the plugin: .cursor/mcp.json and ~/.cursor/mcp.json

The rules it keeps

  • Plain registrations. Each server is registered the standard way, as if you had typed claude mcp add-json yourself. Nothing of the plugin sits between the app and the server, so servers keep working if you uninstall it. The one exception is the small bridge described below, which lives in your root folder.
  • A server is recognised by what it launches (its package, or its URL), not by its name. A tool you renamed is still found, and a server of your own is never mistaken for one of the plugin's.
  • Your entries in Cursor stay. A server you added to Cursor's file yourself is kept in place. A name you already use there is replaced only after a question.
  • Pinned versions. Each package is fixed to an exact version that was at least 7 days old when it was chosen, so a release published an hour ago never runs on your machine unreviewed.
  • Absolute paths. Every path the plugin writes is absolute, so a session started in a subfolder uses the same profile, index and database.
  • Prepared before first use. Claude Code gives a server 30 seconds to answer, and a first download can take minutes. Install downloads each package and starts the server once in the background, so your next session connects in time.

One sign-in for both apps

gitlab, atlassian and sentry's hosted route sign in with OAuth when you give them no key. Set up for both apps, each runs through mcp-remote with its sign-in folder set to the root, so you sign in once in the browser and both apps use it.

  • The sign-in files are in <root>/mcp-remote-v1/. They are tokens: the plugin never reads, prints or copies them, the root's .gitignore keeps them out of git, and a deny rule keeps AI sessions out of the folder.
  • To sign out, delete that folder. The next start opens the browser again.
  • If the sign-in fails in both apps, the vendor may have turned this kind of sign-in off. Use a key instead: /alfred-tools:configure <tool>, then 'Use a key from .mcps-secrets'.

The Sentry bridge: one organization and project

Sentry's hosted server is limited to an organization and a project only through its URL. The 'Bridge' route builds that URL from .mcps-secrets each time the server starts, so switching projects is: change a line, then restart.

  1. Run /alfred-tools:install sentry, choose 'Set sentry up' and the route 'Bridge'. Project scope is recommended here: the registration holds names only.
  2. Keep the names it offers: SENTRY_ACCESS_TOKEN, SENTRY_ORG and SENTRY_PROJECT.
  3. Fill them in the .mcps-secrets the plan names. Leave SENTRY_PROJECT empty for the whole organization.
  4. Restart Claude Code, or Reconnect the server in /mcp. Do the same after each change to these lines.
SENTRY_ACCESS_TOKEN=sntryu_...
SENTRY_ORG=my-org
SENTRY_PROJECT=my-project

The server does not start until the key and the organization are filled. A wrong token shows at the first tool call, as Sentry's own error.

Where the files go

Everything the plugin writes sits in one of two root folders. Install asks for each one once.

  • The project root, for Project and Local scope: .alfred-tools in your project (.alfred when alfred-code is set up there), or a folder you name.
  • The global root, for Global scope: ~/.alfred-tools (~/.alfred when it exists), or a folder you name.
.alfred-tools/
  .mcps-secrets          your keys - you write the values
  mcps.json              the list of servers the plugin manages here
  mcp-headers.js         the key helper for hosted servers
  mcp-bridge.js          the bridge - only when a server needs it
  package.json           lets the two scripts load in any project
  serena-context.yml     serena's navigation-only setup
  .gitignore             keeps keys, sign-ins and data out of git
  mcp-remote-v1/         OAuth sign-ins, after the first one
  serena/                one data folder per tool
  memory/
  playwright-chrome/

The only files outside a root are the apps' own: .mcp.json and your account file for Claude Code, .cursor/mcp.json and ~/.cursor/mcp.json for Cursor.

When something is wrong

Run /alfred-tools:fix first. It knows most of these and applies the recorded fix after you confirm.
